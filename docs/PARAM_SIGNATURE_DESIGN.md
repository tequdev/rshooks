# Hook Parameter Signature Interface — rshooks design

Status: approved direction, implementation in progress. The surface this
document describes ships behind the `unstable-param-sig-interface` Cargo
feature (default off), since the interface itself is still a draft.

This document specifies how rshooks implements the **Hook Parameter
Signature Interface** draft: a `HookParameterName` convention that exposes a
Hook's parameters as a machine-readable, typed function signature.

The wire convention (normative, from the interface draft):

```
HookParameterName = 0x5F 0x50 0x53       ; "_PS" interface identifier
                  | 0x00                  ; version
                  | index    (1 byte, 0x00..=0x0F, raw binary)
                  | type     (1 byte, an XAS-010d type code, raw binary)
                  | name_len (1 byte, 0x01..=0x10 = name.len())
                  | name     (1..=16 bytes, [A-Za-z][A-Za-z0-9]*)
```

Total 8..=23 octets. The type byte is a **type code as defined by XAS-010d
(Hook Type Codes, <https://github.com/Xahau/xahaud/discussions/798>)**: codes
`0x00..=0x7F` are standard types mirroring `SField.h`'s `STI_*` serialized
type codes; `0x80..=0xFF` are Hook-specific non-standard types with no
`SField.h` counterpart (currently only `0x80` `XFL`). XAS-010d also fixes
each type's canonical value encoding — the value bytes alone, with no field
ID, type prefix, or length prefix; the interface draft lists the supported
subset (§2). Declaration entries (on the `Hook`/`HookDefinition`
object, i.e. in the SetHook JSON) carry `HookParameterValue = 0x00`.
Invocation entries (transaction common `HookParameters`) carry the typed
argument value, read inside the hook via `otxn_param` with the full declared
name. Every declared parameter is REQUIRED; indices must be exactly
`0x00..N-1`; display names must be unique.

## 1. User-facing surface: hook fn arguments

The primary surface is the entry fn's own signature. Extra arguments after
`&self` on a `#[hook(..)]` fn declare the signature parameters:

```rust
#[hooks]
impl Increment {
    /// increment(account: AccountID, count: UInt16)
    #[hook(0, on = [Invoke])]
    fn increment(&self, account: AccountId, count: u16) -> HookResult {
        // `account` and `count` are already decoded here.
        ...
    }
}
```

- **index** = argument position (0-based, `&self` excluded). Contiguity and
  uniqueness (`0x00..N-1`) hold by construction.
- **display name** = the argument identifier, validated at macro time
  against `[A-Za-z][A-Za-z0-9]*` and 1..=16 octets (so a Rust ident with
  `_` is a compile error at the attribute's span).
- **type code** = derived from the argument type (table below). The macro
  maps the *type token* to the byte at macro time (for the carrier) and
  additionally emits a monomorphized `const` assert that the token-level
  byte equals `<Ty as SigParamType>::TYPE_BYTE`, so a type alias or drift
  fails the build instead of silently mis-declaring.
- At most 16 arguments (`0x00..=0x0F`); a 17th is a macro-time error.
- `#[cbak(..)]` fns MUST NOT declare extra arguments (macro-time error):
  the callback's originating transaction is the emitted txn, not the
  invocation.
- Entry fns without extra arguments are completely unaffected (no sig, no
  declarations emitted, byte-identical wasm — verified by the parity
  probe).

### Generated prologue

For each argument, the export wrapper generated by `#[hooks] impl`:

1. Builds the full declared name as a `const` byte array (compile-time,
   `padded_bytes`-style `const fn`, no runtime work).
2. Reads it via `otxn_sig_param` (`crates/rshooks/src/sig.rs`) — the plain
   `otxn_param` path, not the `otxn_param_raw_code`-based one
   docs/TODO.md's nesting rule warns about. That rule's actual trigger is
   *matching a specific decoded `HookError` variant* at a call site (24 →
   70 nesting, measured); the generated prologue never does that — its
   `Err(_) => rollback!(..)` arm discards whichever variant `otxn_param`'s
   own `res()` produced, exactly like every other `?`-free "any failure →
   rollback" call site in this crate. Measured through the real build:
   `examples/19_param-signature`'s single entry stays at nesting depth 1.
   Two development-time conversions (not committed — 12/16 stay on the
   stable parameter API; see §5) put numbers on the cost of adding
   signature-parameter arguments to a larger, already-instrumented hook: a
   two-argument conversion of `examples/12_typed-data`'s one 9-byte
   `#[otxn_param(..)]` struct read moved nesting 14 → 15, still well
   inside the 32-level budget, and converting `examples/16_typed-results`'s
   own `#[otxn_param(..)]` field to a signature parameter made its WCE
   *fall* (307 → 306, one instruction lower). The raw-code path was
   unnecessary caution here, not a requirement.
3. Decodes per the declared type (see §2; integers are **big-endian** —
   this is a protocol-facing boundary, DESIGN.md §5.6 applies, unlike the
   hook-private little-endian `FromBytes` convention).
4. On absence, wrong length, or an undecodable value: `rollback` with the
   message `b"rshooks: bad sig param '<name>'"` and code = the parameter
   index (as i64). The body never runs with a partially-decoded signature.

## 2. Supported types (`SigParamType`)

New trait in `crates/rshooks/src/sig.rs`:

```rust
pub trait SigParamType: Sized {
    /// The XAS-010d type code advertised in the declared name.
    const TYPE_BYTE: u8;
    /// Decodes the invocation value payload (already length-delimited by
    /// the host). Err on wrong length / undecodable payload.
    fn read_sig(read: impl FnOnce(&mut [u8]) -> Result<usize>) -> Result<Self>;
}
```

| Rust type | Type code | Payload |
|---|---|---|
| `u8` | `0x10` STI_UINT8 | 1 byte |
| `u16` | `0x01` STI_UINT16 | 2 bytes BE |
| `u32` | `0x02` STI_UINT32 | 4 bytes BE |
| `u64` | `0x03` STI_UINT64 | 8 bytes BE |
| `[u8; 16]` | `0x04` STI_UINT128 | 16 bytes |
| `[u8; 32]` / `Hash` | `0x05` STI_UINT256 | 32 bytes |
| `AmountBytes` | `0x06` STI_AMOUNT | 8 (native) or 48 (IOU) bytes |
| `Blob<N>` (new) | `0x07` STI_VL | 1..=min(N, 256) raw bytes |
| `AccountId` | `0x08` STI_ACCOUNT | 20 bytes |
| `[u8; 20]` | `0x11` STI_UINT160 | 20 bytes |
| `IssueBytes` (new) | `0x18` STI_ISSUE | 20 bytes (all-zero = native) or 40 (currency+issuer) |
| `CurrencyCode` | `0x1A` STI_CURRENCY | 20 bytes |
| `XFL` (`rshooks::xfl::XFL`) | `0x80` XFL | 8 bytes BE (raw `int64` bits) |

`XFL` is XAS-010d's one non-standard code. Its value encoding is the Hook
API's `int64_t` XFL bit pattern, big-endian — i.e. `XFL::raw_bits()` as
`to_be_bytes()`; the canonical zero is eight `0x00` bytes, which is exactly
`XFL::from_raw_bits(0)`. The decode is `XFL::from_raw_bits(i64::from_be_bytes(..))`
on an exactly-8-byte payload (any other length is `TooSmall`), with **no
validity check** of the bit pattern — the same opaque-bits contract
`XFL::from_raw_bits` itself documents; validating would cost a host call.
This impl deliberately does **not** reuse `XFL`'s `FixedRead`/`FromBytes`
impls: those are the hook-private little-endian memory-image convention
(`convert.rs`), the wrong byte order for this protocol-facing boundary. The
macro recognizes the bare token `XFL` (the user imports `rshooks::xfl::XFL`;
the `XFL!` literal macro lives in a different namespace, so both imports
coexist).

New types in `crates/rshooks/src/sig.rs` (or `types.rs`, implementer's
call, following the module doc conventions):

- `Blob<const N: usize> { len: usize, bytes: [u8; N] }` with `as_bytes()`.
  A zero-length value cannot occur (`otxn_param` treats empty as absent —
  absence already rollbacks), but decode still guards `1..=N`.
- `IssueBytes { Native, Issued(IssuedAsset) }` — 20 all-zero bytes decode
  to `Native`; 20 non-zero bytes are an error (per the draft, native issue
  is exactly 20 zero bytes); 40 bytes decode to `Issued`.

Unsupported type codes (`STI_NUMBER` etc.) simply have no `SigParamType`
impl; using such a type as an entry-fn argument is a macro-time error
(unknown token) or a trait-bound error.

## 3. Low-level escape hatch

Per the standing rule (docs/TODO.md), every macro surface has a raw
counterpart. `crates/rshooks/src/sig.rs` exports:

```rust
/// Builds a declared name at compile time; const-asserts every MUST of the
/// wire format (name charset/length, supported type byte, index <= 0x0F).
pub const fn sig_param_name<const N: usize>(index: u8, type_byte: u8, name: &[u8]) -> [u8; N];

/// `sig_name!(0, u16, b"count")` → `[u8; 12]` const, usable directly with
/// `otxn_param_exact` / `hook_param_exact`.
macro_rules! sig_name { .. }
```

plus `SigName<V: SigParamType>` implementing `TypedParamName` so
`otxn_param_typed(&SIG)` works for hand-rolled reads.

## 4. Carrier and SetHook template emission

### Carrier (`rshooks-macros` → `rshooks-build/src/carriers.rs`)

The macro emits the `sig_params` carrier key only when `rshooks-macros` is
built with `unstable-param-sig-interface`; the feature flows
`rshooks` → `rshooks-macros`. `EntryDecl` mirrors that as an `Option`
(serde `default`, so a carrier with no key still parses):

```rust
sig_params: Option<Vec<SigParamDecl>>,
// SigParamDecl { field: String, type_byte: u8, name_hex: String }
```

`None` means the key is absent (the hook was built without the feature);
`Some(list)`, possibly empty, means the key is present. `name_hex` is the
full resolved declared name (8..=23 bytes) as uppercase hex — resolved at
macro time so the build tool never re-derives it. Index is the vec
position. Both `encode_*_json` in the macro crate and `carriers.rs` change
together (`deny_unknown_fields` + `assert_carriers_match` police drift).

### SetHook template (`rshooks-build/src/sethook_template.rs`)

For every entry whose `sig_params` is non-empty, `HookEntryTemplate` emits
(key order: insert between `HookApiVersion` and `HookName`):

```jsonc
"HookParameters": [
  { "HookParameter": { "HookParameterName": "<name_hex>", "HookParameterValue": "00" } },
  ...
]
```

sorted by index. Entries with no sig params emit no `HookParameters` at
all, and gap entries stay exactly `{"Hook": {}}` — the settled decision
(MULTI_HOOK_STRUCT_DESIGN.md §9 point #10, "HookParameters is never
generated") is **superseded only for declared signature parameters**, which
is exactly the reopen condition recorded as open question D5 ("extraction
via the wasm carrier"). Ordinary `#[hook_param]`/`#[otxn_param]` fields are
still never emitted. Update MULTI_HOOK_STRUCT_DESIGN.md accordingly.

The sidecar metadata JSON (`entry_sidecar.rs`) emits the same `sig_params`
verbatim, and only when the carrier has one — the key is present iff the
hook was built with `unstable-param-sig-interface`.

## 5. Example changes

- `examples/19_param-signature` (new): the draft's own example,
  `increment(account: AccountID, count: UInt16)` — adds `count` to a
  per-`account` counter in hook state. Demonstrates the generated
  declarations in `sethook.template.json` and typed invocation in e2e.
  This is the only committed example that enables the
  `unstable-param-sig-interface` feature (see its own `Cargo.toml`).
- `examples/12_typed-data` and `examples/16_typed-results` remain on the
  stable parameter API (`#[hook_param]`/`#[otxn_param]` struct fields) —
  converting either to signature-parameter fn arguments was explored
  during development (see §1's nesting/WCE numbers) but not committed, so
  neither example declares signature parameters in-tree.
- NOT converted, with reasons documented in their READMEs where relevant:
  `15_slot-objects` (`CHK` has a default — the interface has no optional
  parameters), `80_governance` (dynamic composite names like `"T"+topic`
  are inexpressible as declared signatures), `03_hook-params`
  (install-time `hook_param` configuration, out of the interface's
  invocation scope).

## 6. Validation & tests

- Macro-time (trybuild fail fixtures + pinned `.stderr`): name with `_` /
  non-ASCII / >16 octets / >16 args / sig args on `#[cbak]` / unsupported
  type token.
- Const-time: `sig_param_name` asserts inside `const {}` (charset, length,
  index range, supported type byte).
- Unit tests: name codec vectors from the draft's test-vector table;
  `SigParamType` decode round-trips including AmountBytes 8/48, IssueBytes
  20-zero/20-nonzero-err/40/44-MPT-shaped-err (the read buffer is sized to
  44 — an MPT issue's own length, `crate::slot_obj::ISSUE_MAX_READ_LEN` —
  precisely so a 44-byte value is read and rejected as `ParseError` rather
  than surfacing as a host-call `TooSmall`, the same rationale
  `decode_issue`'s doc comment gives for the slot-read path this mirrors),
  Blob bounds, `XFL` (8 BE bytes ↔ `raw_bits`, `XFL!(1)`'s
  `0x54838D7EA4C68000` → `54 83 8D 7E A4 C6 80 00`; zero ↔ eight `0x00`;
  7 or 9 bytes → `TooSmall`).
- testenv: seed `Otxn::param` with encoded names/values; absence and
  wrong-length paths assert the generated rollback (message + index code).
- Parity probe + WCE/size/nesting before/after numbers, measured during
  development against candidate conversions (docs/TODO.md standing rule;
  see §1's numbers and §5's note on which examples are actually committed).

## 7. Cargo feature gate

The entire surface — `rshooks::sig`, and extra `ident: Type` arguments on
a `#[hook(..)]` entry fn — is gated behind the `unstable-param-sig-interface`
Cargo feature (default off): `crates/rshooks/Cargo.toml` forwards it to
`crates/rshooks-macros/Cargo.toml`'s feature of the same name. Off, an
extra argument on `#[hook(..)]` is a compile error naming the feature, and
`rshooks::sig` doesn't exist; `#[cbak(..)]` extras still get their own
unconditional rejection (§1's "MUST NOT declare extra arguments") in both
configurations, since that restriction doesn't depend on the interface
being available at all. `unstable-*` features are exempt from semver — the
interface may change in a breaking way in a minor release while it stays a
draft.
