# firewall

Reads the originating transaction's sender (`otxn_field(sfAccount)`) and a
Hook parameter named `BL` (the blocked `AccountId`, 20 bytes). Rolls the
transaction back if they match; accepts otherwise (including when `BL`
isn't configured — nothing to block). Straight-line code: no loop is
written in the source, so no `guard!` is needed there.

## Build

```sh
cargo run -p rshooks-build -- build --manifest-path examples/05_firewall/Cargo.toml
```

No extra flags needed. Comparing two bare `[u8; 20]` buffers with `==`
would compile to a compiler-generated byte-compare loop (`bcmp`) under
`opt-level = "z"` on `wasm32v1-none` (no bulk-memory instructions to do it
inline), requiring `--auto-guard --default-maxiter 24` (24, not the
`--auto-guard` default of 16, because the loop's true worst case is 20
iterations — one per byte; getting that number wrong builds fine but risks
a runtime `GUARD_VIOLATION` on a real node). `AccountId`'s own `==` no
longer hits this pitfall: `rshooks::types::AccountId`'s `PartialEq` is
hand-written to delegate to
[`rshooks::buf_eq_20`](../../crates/rshooks/src/buf_eq.rs) internally, so
`sender == blocked` would itself already be loop-free. This example
compares with `buf_eq_20` explicitly anyway, to keep the loop-free
mechanism visible at the call site rather than relying on the type's
`PartialEq` impl — see `rshooks::buf_eq`'s module docs for why a generic
`buf_eq<const N: usize>` isn't offered instead. See `examples/README.md`'s
"On `--auto-guard`" section for the general story (still relevant to other
compiler-generated loop shapes, like `memcpy`/`memset`).

## Configuring the blacklist

Set a `BL` Hook parameter (20 raw bytes, the blocked `AccountId`) when
installing this Hook via `SetHook`. Deployment/SetHook tooling is out of
scope for this repo (see `docs/DESIGN.md` §1 non-goals).

## Error codes

`FirewallError` (`rshooks::hook_errors!`, see `src/lib.rs`) is the
`rollback!` code for each failure this hook can exit with:

| variant | code | meaning |
|---|---|---|
| `CouldNotReadSender` | 1 | `otxn_field(sfAccount)` did not return a 20-byte `AccountId` |
| `BlockedAccount` | 2 | the sender matched the `BL`-configured blacklist account |
| `CouldNotReadBlocklist` | 3 | `BL` is present but not a 20-byte `AccountId`, or the host call otherwise failed (an absent `BL` is not an error: it means nothing to block) |
